# Description

Tests IMAP FETCH literal parsing on a partially one-sided ("oneway")
capture: the connection's original SYN, and anything that would have
preceded it (e.g. a `LOGIN`), was never captured (asymmetric routing, or
a tap that started mid-conversation). The first packet ever observed is
the server's bare SYN/ACK; the only other packets are a single client
ACK completing the picked-up handshake and the server's FETCH literal
response. No IMAP request is ever captured at all.

This proves response-side FETCH literal parsing (`IMAPState.parse_response`
/ `literal_remaining`) does not depend on having observed a matching
request or transaction context - a single `fileinfo` event with the
correct `size: 16` is produced from the response alone.

`stream.async-oneside` (the more obvious "one-sided flow" setting) was
tried first, but does not work for this toclient-only shape: it only
learns a real TCP window for whichever side sent the original SYN, and
unconditionally drops its relaxed validation the instant a packet from
the *other* side appears - so the server's first (and only) data packet
gets rejected as out-of-window before app-layer ever sees it (confirmed
by direct debugging of `src/stream-tcp.c`). `stream.midstream`, entered
via a bare SYN/ACK, correctly learns the server's window up front and is
used here instead, together with `stream.midstream-policy=pass-flow` to
permit the pickup (the default `midstream-policy` does not).
