# Description

Request-side (client->server) mirror of `imap-literal-gap-mid-literal`:
proves `IMAPState::on_request_gap()`'s file-truncation fix -- shipped in
the same change that adds APPEND extraction, not left for a follow-up --
actually works, rather than being untested the way the response-side gap
fix briefly was.

The pcap drops the second half of an APPEND literal outright (a real
`STREAM_GAP` on the TOSERVER side, not just a benign multi-packet split --
contrast with `imap-append-multi-segment`, which keeps both halves), then
sends a second, complete, in-sync APPEND immediately after.

Expected behavior:
- The gapped upload: `state: TRUNCATED`, `size: 32` (only the bytes
  actually delivered before the gap).
- The second APPEND's file: its own independent `state: CLOSED`,
  `size: 64` -- proof the new upload is not corrupted by gap leftovers
  from the first one, mirroring the exact fix verified for FETCH.
- Zero IMAP parser errors.

Also exercises `filestore` on both files: both the TRUNCATED and the
CLOSED upload are confirmed `stored: true` with their exact byte content
pinned by `sha256`, now that IMAP's file-detection engines are registered
for both directions (see `imap-append-basic/README.md`).

# PCAP

Synthetic pcap generated by `gen_pcap.py` (scapy), modeled on
`imap-literal-gap-mid-literal`. Regenerate with `python3 gen_pcap.py`.
