# Description

Baseline coverage for IMAP `APPEND` (client uploads a full message to the
server using the same `{n}` literal syntax FETCH responses already use, but
in the opposite direction): LOGIN followed by a single-segment APPEND with
a `{n}` literal, entirely in one TCP segment per direction.

Proves the request-side (client->server) literal extraction path added to
`rust/src/applayerimap/` works: the uploaded message produces its own
`fileinfo` event, distinguished from a FETCH download by filename
(`appendmsg` vs `rawmsg`) since `fileinfo` events carry no direction field.

Also proves `filestore` fires on the uploaded (TOSERVER) file:
`src/detect-file-data.c`'s file-detection-engine registration for IMAP used
to be TOCLIENT-only, so `filestore` (and `file_data`, `filemd5/sha1/sha256`,
etc.) silently never fired for a TOSERVER file -- the rule loaded without
error and simply never stored anything. Now that registration covers both
directions, `test.rules`' bare `filestore` rule (no explicit `flow:`
direction) stores the APPEND upload, asserted via `fileinfo.stored: true`.

# PCAP

Synthetic pcap generated by `gen_pcap.py` (scapy), modeled on
`imap-literal-basic`. Regenerate with `python3 gen_pcap.py`.
