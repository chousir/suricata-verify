# Description

Tests that an APPEND literal split across two client->server TCP segments
is reassembled using the declared `{n}` byte count -- the request-side
mirror of `imap-literal-multi-segment`'s response-side (FETCH) coverage.

The literal is 46 octets (same content as `imap-literal-multi-segment`,
confirmed by an identical `sha256`); the pcap splits the APPEND command
mid-literal (not on a CRLF boundary) into two TCP segments, so
`IMAPState.request_literal_remaining` must persist the outstanding octet
count from the first `parse_request()` call to the second. A single
`fileinfo` event with `size: 46` proves the two segments were joined into
one logical literal.

Also exercises `filestore` on the reassembled upload (`fileinfo.stored: true`),
now that IMAP's file-detection engines are registered for both directions
(see `imap-append-basic/README.md`).

# PCAP

Synthetic pcap generated by `gen_pcap.py` (scapy), modeled on
`imap-literal-multi-segment`. Regenerate with `python3 gen_pcap.py`.
