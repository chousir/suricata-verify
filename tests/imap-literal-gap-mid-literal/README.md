# Description

Regression test for a confirmed data-corruption bug in gap handling:
`IMAPState::on_response_gap()` used to only set a `response_gap` bool
flag without resetting `literal_remaining` or truncating the currently
open file tracker. When the next, unrelated FETCH response arrived and
passed the `probe()` resync check, the parser resumed consuming
`literal_remaining` bytes from that *new* response as leftover content
of the *old* (gapped) file -- silently corrupting the old file (falsely
reported `CLOSED`/`gaps:false`) while the new message's own extraction
vanished entirely (no `fileinfo` event at all).

The pcap drops the second half of a FETCH literal outright (a real
`STREAM_GAP`, not just a benign multi-packet split -- contrast with
`imap-literal-multi-segment`, which keeps both halves), then sends a
second, complete, in-sync FETCH immediately after.

Expected behavior after the fix:
- The gapped file: `state: TRUNCATED`, `size: 33` (only the bytes
  actually delivered before the gap).
- The second FETCH's file: its own independent `state: CLOSED`,
  `size: 65` -- proof the new message is no longer swallowed by the
  stale `literal_remaining` counter.
- Zero IMAP parser errors.

# PCAP

Synthetic pcap generated by `gen_pcap.py` (scapy), modeled on
`imap-literal-multi-segment`. Regenerate with `python3 gen_pcap.py`.
