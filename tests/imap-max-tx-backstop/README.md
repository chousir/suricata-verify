# Description

Regression test for `IMAPState::new_tx()`'s `IMAP_MAX_TX` backstop
(`rust/src/applayerimap/imap.rs`): `app-layer.protocols.imap.max-tx` was
read from the config but never actually enforced -- a single pathological
TCP segment packed with many trivially-complete commands (e.g. LOGIN,
which creates an AUTH transaction that's marked done in both directions
the instant it's parsed, without waiting for a response) could drive an
unbounded burst of transaction allocations within one `parse_request()`
call, before the next `AppLayerParserTransactionsCleanup` pass even gets a
chance to prune anything.

The pcap sends 20 `LOGIN` commands back to back in a single segment, none
of which ever get a response. With `imap.max-tx` lowered to 5, `new_tx()`
must refuse to allocate past the 6th transaction (`flow.tx_cnt: 6`, not
20) and raise the `too_many_transactions` app-layer event on every
refused allocation (14 of them: 20 attempts minus the 6 that succeeded).

Unlike POP3's equivalent backstop (which this mirrors), an IMAP AUTH
transaction is already "done" the moment it's created, so a burst made
entirely of LOGINs never has an existing *incomplete* transaction to
force-complete -- `new_tx()` therefore always raises
`too_many_transactions` when it refuses an allocation, not only when it
had to force one closed. Confirmed the flow's app-layer parser does not
enter an error state (`stats.app_layer.error.imap.parser: 0`) -- hitting
the cap is a soft limit, not a fatal parser error, matching the intent of
`bug-8629-async-oneside` (a similar backstop for SMB) rather than the
pre-fix SMB behavior that test guards against.
