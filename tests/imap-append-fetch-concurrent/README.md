# Description

The cross-direction-contamination guard test: a FETCH response literal is
left half-delivered (`literal_remaining > 0`) while a complete, unrelated
APPEND request literal (different size, different content) is sent and
fully consumed on the same flow, before the FETCH literal's remaining
bytes arrive. Proves `IMAPState.literal_remaining` (response/FETCH) and
`IMAPState.request_literal_remaining` (request/APPEND) never interfere
with each other, and that both files extract independently and correctly
even when genuinely in flight at the same time.

This test caught a real bug during development, distinct from the counter
separation it was originally designed to guard: `IMAPState::find_file_tx()`
used to require the matching file transaction to be the single most
recently created transaction overall (`tx.tx_id == self.tx_id`). That
invariant silently broke the moment a transaction in the *other* direction
was created afterward -- the older, still-open file's transaction became
permanently unfindable, its remaining bytes were dropped
(`filetracker_update`/`close` became no-ops), and it was later
force-truncated at flow teardown instead of closing normally. Fixed by
having `find_file_tx` search for the most recent transaction *of the
requested direction* specifically (searching from the newest transaction
backwards) rather than the newest transaction overall.

Expected result: two independent `fileinfo` events, each `state: CLOSED`
with its own correct `size`/`sha256`/`filename` (`rawmsg` for the FETCH,
`appendmsg` for the APPEND), zero parser errors. Before the `find_file_tx`
fix, the FETCH file came out `state: TRUNCATED` with only the bytes
delivered before the APPEND interleaved (10 of 19), and the APPEND file
was unaffected -- so this test would have failed on exactly the first
assertion.

Also exercises `filestore` on both files at once: a single bare `filestore`
rule (no explicit `flow:` direction, see `imap-append-basic/README.md`)
stores the TOCLIENT FETCH download and the TOSERVER APPEND upload
concurrently, asserted via `fileinfo.stored: true` on both events -- good
combined coverage of the `find_file_tx` fix above plus IMAP's file
inspection engines now being registered for both directions.
